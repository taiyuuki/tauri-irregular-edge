# tauri-irregular-edge

验证 Tauri 2 的透明窗口能不能做出输入法皮肤那样的效果：不规则轮廓、半透明图片、九宫格拉伸，
以及轮廓之外的区域能不能点击穿透。

在两个平台上验证过，用的都是 Tauri 2.12.7（tao 0.37.3、wry 0.57.4）：

- macOS 27.2.1（Apple Silicon），主显示器 1920×1080、缩放 1x
- Windows 11（内部版本 26300），WebView2 158.0.4370.33，主显示器 2560×1440、缩放 150%

Linux 没有测。

## 结论

- **不规则轮廓可行，两个平台都是。** 屏幕上的像素和“皮肤图叠在背后窗口上”的理论值逐像素吻合：
  macOS 上本体、阴影、抗锯齿边缘的最大误差是 0–1/255，Windows 上是 0/255。
- **九宫格拉伸可行。** 窗口从 349 拉高到 469 逻辑像素后，圆角、缺口、尾巴都保持原样。
  Windows 上是在 150% 缩放下测的：2x 的皮肤图按 1.5 倍显示，结果一样。
- **点击穿透能做，但 Tauri 没有内置，要自己实现。** 这里用的做法是轮询光标位置，按命中掩码切换“忽略鼠标事件”。
  从光标越过轮廓到切换生效有一个时间窗，但两个平台上差别很大：
  - macOS：10–20 毫秒，这期间点击会被面板的透明部分吃掉。
  - Windows：0–8 毫秒，被吃掉的点击一次都没有测到（502 次甩动里 0 次）。
- **切换穿透的瞬间，点击会凭空丢失，两个平台都有。** macOS 上 102 次甩动里丢了 11–13 次。
  Windows 上 502 次里丢了 22 次（4%），全部是光标刚越界 2 毫秒之内就按下的；等 3 毫秒以上再按的 284 次，一次都没丢。
- **Windows 上切换穿透不会让画面闪。** 那里每切换一次都要改窗口样式，本来担心画面会跳一下，实测没有。

## 运行

```sh
pnpm install
pnpm tauri dev                          # 开发模式，屏幕中央弹出一个异形面板
pnpm tauri build --debug --no-bundle    # 只编译，产物给下面两个脚本用

scripts/verify.sh                       # 一键验证：像素检查 + 点击穿透
scripts/race-window.sh                  # 单独测点击穿透的时间窗（需要 python3，Windows 上命令是 python）
PROFILE=release scripts/verify.sh       # 换成正式构建（先 pnpm tauri build --no-bundle）
```

两个脚本在 macOS 和 Windows（Git Bash）上都能跑，验证工具用系统自带的编译器编，不用另装 SDK。
它们都会临时启动面板和一个独立进程里的原生棋盘格窗口，运行期间会移动鼠标、模拟点击，结束时自动关闭。

**运行期间不要动鼠标。** 面板右下角的状态文字跟着光标变，截图时鼠标一动，三次截图的面板内容就不一样了。
`capture` 发现光标离开过停放位置会自动重截（最多三次）；鼠标动了又回到原处的情况由 `analyze` 里
“三次截图之间面板内容没变”那一项报出来。

`IRREGULAR_HIT_MODE=js scripts/verify.sh` 可以换成“由前端调回去切换穿透”的做法来对比。

## 两个平台上各是怎么实现的

同一份配置（`transparent`、无边框、无阴影），底下的机制不一样。下面的说法来自 tao 和 wry 的源码，
以及对面板窗口扩展样式的实际读取。

| | macOS | Windows |
| --- | --- | --- |
| 透明 | WKWebView 关掉 `drawsBackground`、`setOpaque(false)` | tao 调 `DwmEnableBlurBehindWindow` 并给一个空区域，让 DWM 按每个像素的 alpha 合成窗口；wry 把 WebView2 的背景设成透明。窗口**不是**分层窗口（没有 `WS_EX_LAYERED`） |
| 点击穿透 | `NSWindow.setIgnoresMouseEvents` | `set_ignore_cursor_events(true)` 给窗口**加上** `WS_EX_LAYERED \| WS_EX_TRANSPARENT`，设回 false 再去掉 |
| 截单个窗口（带 alpha） | `screencapture -l` | `PrintWindow` 截出来 alpha 通道全是 255，透明处变成黑色，拿不到 alpha |

所以 Windows 上光标每进出轮廓一次，窗口样式就变一次。这是第 6 条要测的东西。

```
  assets/panel@2x.png                皮肤图：四个圆角半径不同，底部一个尖角，右侧一个内凹缺口，
                                     本体 alpha 0.78，阴影烘在图里
src-tauri/
  tauri.conf.json                    窗口：transparent、无边框、无阴影、置顶、初始不可见
  src/lib.rs                         轮询光标位置；按命中掩码切换“忽略鼠标事件”
scripts/
  gen-panel-png.mjs                  生成皮肤图（带符号距离场画轮廓，高斯模糊画阴影）
  probe.swift, backdrop.swift        macOS 上的验证工具：截屏、像素测量、合成鼠标事件；背后的棋盘格窗口
  probe.cs, backdrop.cs              Windows 上同样的两个工具，用系统自带的 .NET Framework 编译器编
  verify.sh, race-window.sh          验证流程，两个平台通用
verification/                        最近一次运行的截图和输出
  initial-*, resized-*               macOS（调试版）
  win-*                              Windows（调试版）

```

Windows 上每个标签比 macOS 多两张图：`*-screen-black.png`、`*-screen-white.png` 是面板分别叠在纯黑、纯白背景上的截图，
`*-panel.png` 是由这两张反推出来的（原因见上表）。`win-verify-*.txt`、`win-race-*.txt` 是脚本的实际输出。

## 验证方法和结果

### macOS

| 验证项 | 怎么测 | 结果 |
| --- | --- | --- |
| 不规则轮廓 | 截取面板矩形范围内的屏幕，和“面板窗口截图 × 背后棋盘格”的理论合成值逐像素比较 | 轮廓之外的 42325 个像素就是纯黑或纯白的棋盘格，最大误差 1/255 |
| 半透明本体 | 同上；再用棋盘格透过本体后剩下的对比度反推不透明度 | 本体 alpha 199（设计值 199）；反推不透明度 0.78（设计值 0.78）；本体内部最大误差 0/255 |
| 柔和阴影 | 面板窗口自身截图的 alpha 通道 | 本体下方阴影 alpha 峰值 88、尾巴两侧 88，逐级渐变；屏幕上最大误差 1/255 |
| 九宫格拉伸 | 点三次“+ 一行”把窗口拉高到 469，重新截屏比对 | 同样全部通过 |
| 停稳后点击穿透 | 光标停 300ms 后点击左上角、本体下方阴影、右侧缺口、右上圆角外 | 4 次全部落到背后另一个进程的窗口 |
| 越界后立刻点击 | 甩到透明处后不到 1ms 按下，三个目标点各 10 次 | 30 次全部被面板吃掉 |
| 时间窗 | 到达后等 N 毫秒再按下，每个 N 做 6–10 次 | 等 0–3ms 全部失败；11–19ms 大部分成功，偶尔失败；20ms 以上没有再失败 |

### Windows

显示器缩放 150%，面板 552×349 逻辑像素对应 828×524 物理像素。调试版完整跑了三遍、正式构建跑了一遍，结果一致。
调试版另外用 `race-window.sh` 测了两遍时间窗，native 和 js 两种切换方式各一遍。

| 验证项 | 怎么测 | 结果 |
| --- | --- | --- |
| 不规则轮廓 | 屏幕截图和“面板自己的颜色与 alpha × 棋盘格”逐像素比较；面板的 alpha 由叠在纯黑、纯白上的两张截图相减得到 | 轮廓之外的 97089 个像素（22.4%）就是纯黑或纯白的棋盘格，最大误差 0/255 |
| 半透明本体 | 同上 | 本体 alpha 199（设计值 199）；反推不透明度 0.78（设计值 0.78）；本体内部最大误差 0/255 |
| 柔和阴影 | 同上 | 本体下方阴影 alpha 峰值 88、尾巴两侧 88，逐级渐变；屏幕上最大误差 0/255 |
| 九宫格拉伸 | 同 macOS | 同样全部通过；拉高到 469 后轮廓之外 105431 个像素，最大误差 0/255 |
| 停稳后点击穿透 | 同 macOS | 4 次全部落到背后另一个进程的窗口 |
| 甩动测试 | 从本体内部甩到透明处，到达后等 0–40 毫秒再按下 | `verify.sh` 共 400 次：被面板吃掉 0 次，两边都没收到 20 次（按等待时间分开见下表） |
| 时间窗（native） | `race-window.sh`，到达后等 0–16 毫秒再按下，每个延迟 6 次 | 光标到达后 1 毫秒以上再按的 96 次全部穿透成功；被吃掉 0 次，丢失 2 次（都在到达后立刻按下的那 6 次里） |
| 从越界到切换生效 | 光标到达时刻到面板日志记下“开始穿透” | native 0–8 毫秒；js 8–34 毫秒 |
| 时间窗（js） | 同上，102 次 | 被面板吃掉 3 次（都在到达后 0–2 毫秒内按下），丢失 2 次 |
| 切换时闪不闪 | 光标每秒在轮廓里外来回十几次，同时每秒截约 50 帧屏幕，面板上半部分和静止时的画面逐像素比较 | 累计 11 次运行、334 次切换、1032 帧，没有一帧不一样 |

把 Windows 上 native 模式的 502 次甩动放在一起看丢失的点击：

| 光标到达后多久按下 | 次数 | 被面板吃掉 | 两边都没收到 |
| --- | --- | --- | --- |
| 不到 1 毫秒 | 166 | 0 | 20 |
| 1–2 毫秒 | 52 | 0 | 2 |
| 3 毫秒以上 | 284 | 0 | 0 |

正式构建和调试版相比，只量出启动更快：窗口在进程启动后 67 毫秒创建（调试版 500–600 毫秒），
显示出来之后 35 毫秒命中掩码就绪。点击“+ 一行”之后窗口长高要 60–70 毫秒（按下之后算起），两个版本一样。

## 过程中发现的坑

**1. 皮肤图里有三个不同的“边距”，别混用。** 透明边距（36）是皮肤图四周留给阴影的；
九宫格切片（92 / 56 / 66 / 66）等于边距加上这个方向上必须保持原样的部分；
内容区的内边距要让开边距和本体之外的部分（底部的尾巴）。我把内容区按切片值写了两次，
结果搜索框和按钮画到了轮廓外面。

**2. 点击穿透有一个时间窗。** 做法是轮询光标位置，在轮廓外时让窗口忽略鼠标事件。
macOS 上从光标越界到切换生效需要几毫秒（Rust 线程里直接切换是 0–8ms，偶有 30ms 的长尾；
由前端调回去切换是 2–41ms），这期间落下的点击会被面板的透明部分吃掉。
Windows 上切换更快（0–8ms），而且点击是按下之后才由系统决定给谁，
所以被吃掉的一次都没测到；由前端调回去切换同样慢不少（8–34ms），也测到了被吃掉的点击。

**3. 切换瞬间附近，点击会凭空丢失。** macOS 上 102 次甩动里有 11–13 次，面板和背后的窗口都没收到点击。
这些点击都落在“面板开始穿透”的前后几毫秒之内。原因没有查清。Windows 上也有（见上面的表），
但只发生在光标越界后 2 毫秒之内按下的情况。

**4. 面板不是焦点窗口时，第一次点击只是让它拿回焦点。** 这是 WKWebView 的默认行为
（Safari 的背景窗口也一样）。启动器唤出面板时要主动把焦点给它，否则用户的第一下点击会没反应。
Windows 上没有专门测这一条：验证工具每次点击前都先把面板切到前台。

**5. 测点击穿透时，背后的窗口要放在另一个进程里。** 我最初把棋盘格做成同一个应用里的第二个窗口，
两个窗口轮流成为焦点窗口，每次切换焦点的第一次点击都被上面第 4 条吞掉，看起来像是点击被丢了。

**6. Windows 上每切换一次穿透都在改窗口样式，但不会闪。** `set_ignore_cursor_events(true)` 会给窗口加上
`WS_EX_LAYERED | WS_EX_TRANSPARENT`，设回 false 再去掉，所以光标每进出轮廓一次，样式就变一次。
让光标每秒在轮廓里外来回十几次、同时不停地截屏，和静止时的画面逐像素比较，没有一帧不一样。

**7. Windows 上永远有别的窗口“盖”在面板上面。** 例如 Windows 11 自带的 Shell Handwriting Canvas：
全屏、置顶、点击穿透的系统手写画布。这台机器上还有第三方软件的一个 1×1 像素的置顶窗口，
从样式上看不出它不接收鼠标（没被禁用，`WM_NCHITTEST` 也回“客户区”），但系统的 `WindowFromPoint` 会跳过它。
所以检查“面板上面有没有别的窗口”不能去数窗口，要问系统：在它和面板重叠的范围里取 3×3 个点，
看 `WindowFromPoint` 返回谁。macOS 上这类浮层在更高的层级，按层级排除就行。

**8. 逐像素读 `clientWidth` 在 WebView2 上非常慢。** `sendHitMask` 原来在双重循环里对每个像素调一次 `skinAlpha`，
而 `skinAlpha` 每次都读 `root.clientWidth` 和 `root.clientHeight`。每读一次都要确认布局是最新的，
552×429 个像素要 1.4 秒。后果是窗口长高之后，命中掩码有 1.4 秒是过期的。
把这两次读取挪到循环外面之后是 4 毫秒（面板刚显示出来时同理：原来 1.16 秒之后掩码才就绪，现在 36 毫秒）。
在 WKWebView 上有多慢没有量。

**9. 在 Windows 上跑这套验证，工具链有几处坑。**
- Git Bash 的 `$!` 不一定是程序的进程号，有时只是一个中间等待进程的号，`kill` 也结束不了真正的程序。
  所以 Windows 上两个程序都由 `probe launch` 启动、`probe stop` 关闭。
- 系统自带的 csc 只支持 C# 5 的语法，而且不认路径里的正斜杠（会把目录部分丢掉），`-out:` 要写在源文件名前面。
- Windows 上 git 默认设了 `core.autocrlf=true`，会把 `.sh` 检出成 CRLF 换行，Git Bash 就跑不了。所以加了 `.gitattributes`。
- Windows 上 python 默认按系统代码页写标准输出，和脚本的 UTF-8 输出混在一起会乱码，要用 `-X utf8`。

**10. Windows 上 `WM_NCHITTEST` 回 `HTTRANSPARENT` 穿不到别的进程的窗口。** 做了一个单独的实验：
上面的窗口对命中测试一律回 `HTTRANSPARENT`，然后点它。
上下两个窗口在同一个进程、同一个线程里时，点击落到下面的窗口；
两个窗口分属两个进程时，`WindowFromPoint` 也说该给下面的窗口，但下面的窗口根本没收到，点击被丢了
（对照组里上面没有这个窗口时，同样的点击是能收到的）。

## 没有验证的

- Linux。
- 其它缩放比例：macOS 的 Retina（2x），Windows 上 100%、200%，以及多显示器、在不同缩放的显示器之间移动窗口。
- 毛玻璃之类的原生窗口效果，以及它和异形皮肤能不能叠在一起。
- 隐藏后再显示、首帧有没有闪。两个平台上窗口都只显示了一次。
- 安装包（NSIS / MSI）装上去之后的程序。测的是 `tauri build --no-bundle` 编出来的 exe。
- Windows 上给窗口设区域（`SetWindowRgn`）的做法。

## 对正式项目的建议（除了第 10 条的实验，都没有验证）

轮询切换的做法对自用的启动器大概够用。Windows 上被吃掉的点击一次都没测到，丢失的只发生在光标越界后 2 毫秒之内；
macOS 的时间窗有十几毫秒，人一般也不会在光标越过轮廓后这么快点击。

如果想彻底消除时间窗，要用各平台原生的“按像素判断点击归属”的机制，让系统在派发点击的那一刻就做判断：

- macOS：重写内容视图的 `hitTest:`，透明处返回 nil
- Windows：**不能**靠 `WM_NCHITTEST` 回 `HTTRANSPARENT`，它只能让给同一个线程里的窗口（第 10 条）。
  能给别的进程让路的是给窗口设区域（`SetWindowRgn`）：区域外的部分既不画也不接收点击，代价是轮廓外的阴影会被切掉。
- Linux：给窗口设置输入形状区域

这些都需要写少量平台相关的原生代码，这个项目里没有做。
